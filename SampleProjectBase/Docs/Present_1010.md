## 0. 作品概要（30秒で話す用）

- **ジャンル**：中世の鍛冶屋で剣を一本鍛え上げる一人称の鍛造シミュレーション
- **出発点**：『Kingdom Come: Deliverance II』の鍛冶ミニゲームの再現 → 現実の鍛造工程（加熱・鍛打・裏返し・研ぎ・焼入れ）へ拡張
- **環境**：C++ / DirectX 11 / HLSL（学校の教材フレームワークがベース。エンジン不使用）
- **アピールの軸**：
  1. **自作の物理シミュレーション**（ハンマー・金属の流れ・パーティクル・衝突）
  2. **ゲームプレイのシステム設計**（階層型ステートマシン＋データ駆動レシピ）
  3. それを見やすくする**レンダリングパイプライン一式**（リニア空間・HDR・PBR・シャドウ）

## 1. 設計・アーキテクチャ（実装済み）

### 1-1. 階層型ステートマシン（HSM）
- **上位**：シーンの状態（タイトル / プレイ / リザルト）
- **下位**：プレイ中の**工程ステートマシン**＝1工程＝1状態
  - `HeatStep`（加熱）/ `ForgeStep`（鍛打）/ `GrindStep`（研ぎ）/ `QuenchStep`（焼入れ）
- フレームワーク `StateMachine` は前作『statemachinechase』のものを**再利用**
  - 文字列キーで状態を登録、`std::function` で Enter / Update / Exit を持つ
  - 状態機は「いつ遷移するか」を知らない → 遷移の判断は持ち主（SceneForge）側
- **選定理由**：工程が明確に分かれているゲームなので FSM が一番素直。前作で使い慣れており保守しやすい。
- 📁 `StateMachine/`, `StateMachine/Player/*Step.cpp`

### 1-2. データ駆動（レシピ）
- 武器＝「工程の順番＋各工程の案内文」を持つ**データ（`WeaponRecipe` 構造体）**
- **新しい武器を追加する＝レシピを1つ足すだけ。状態機のコードは変えない**
- 同じ工程を何度でも使える（例：鍛打の前と焼入れの前に「加熱」を2回）
- **不採用にした物**：コマンドパターン（undo/replay が不要なので過剰）
- 📁 `GameData/WeaponRecipe.h/.cpp`

### 1-3. シミュレーションと描画の分離（デカップリング）
- 物理・ゲームルール・描画を別クラス／別フォルダに分けた
  - `Physics/`（物理）・`GameLogic/`（汎用ゲームシステム）・`StateMachine/`（制御）・`GameData/`（データ）・`SceneForge/`（描画・指揮）
- 例：`ForgingSim` は「打撃を受けたら鉄がどう変形するか」だけを答え、得点・音・セリフはシーン側が結果（`StrikeOutcome`）を見て決める
- **効果**：見た目を作り直しても（アニメ外注など）ゲームの正しさが崩れない

### 1-4. ステージエディタ（データ駆動の配置）
- 専用シーン `SCENE_STAGE_EDITOR` でクリック選択・XYZ ギズモ（移動ハンドル）で道具を配置
- 配置を `stage_layout.txt` に保存 → ゲーム本編が同じファイルを読む
- マウスからの**レイキャストによるピッキング（逆投影）**、炉を動かすと炭・火の粉が付いてくる**親子関係**
- 📁 `StageEditor.cpp`

### 1-5. AABB アンカーによる自動配置
- モデル読込時に**AABB（軸平行境界ボックス）**を計算し、「金床の上面中心」等のアンカーへ自動で乗せる
- モデルを差し替えても座標の手調整（マジックナンバー）が不要

### 1-6. アセット共有とシーン切替の高速化
- モデルはルートシーンが所有し、サブシーンは参照するだけ（再読込しない）
- テクスチャは**パスをキーにしたキャッシュ（`TextureCache`）**で一度だけデコード
- 結果：シーン切替時の 4〜5 秒の停止を解消

### 1-7. チューニング値の外部化（マジックナンバー排除）
- 数値は名前付き定数・デバッグ UI（ImGui）のスライダ・テキストファイル（`forge_tuning.txt` など）に集約
- F1 で**デバッグ UI**、当たり判定などの見えないシステムは**デバッグ描画**で可視化

## 2. 自作の物理シミュレーション（実装済み・★主なアピールポイント）

### 2-1. ハンマー：ばね-ダンパモデル
- 質量 m のハンマー頭が自然長 restLift のばねに付いているモデル
- 合力＝**復元力（フックの法則 −kx）＋減衰力（−cv）** → 加速度 → **セミインプリシット・オイラー法**で積分
- 打撃時に**力積 J** を与えて初速 v0 = J/m で跳ね上げ → オーバーシュートしてから静止位置に収束
- 剛性 k・減衰 c・質量 m はスライダで調整可（臨界減衰 = 2√(km)）
- **選定理由**：セミインプリシット・オイラーは計算が軽く、陽的オイラーより安定（エネルギーが発散しにくい）
- 📁 `Physics/HammerPhysics.h/.cpp`

### 2-2. 鉄の変形：体積保存のハイトフィールド
- 鉄を**20×6 のグリッド（高さ場）**として持つ（長さ5区画 × 表裏2面で進捗管理）
- 叩いたセルの高さを目標に近づけ、押し出した分を**余剰の少ない近傍セルへ重み付きで再分配**
  - 重みを**正規化**（合計1）するので、金属の総体積が保存される（金属は非圧縮）
- 叩くほど目標形状に**収束**する
- 打撃の結果を `Shaped / ColdHit（冷えている）/ OverHit / AlreadyDone（完成済みの所）` で返す
- 📁 `Physics/ForgingSim.h/.cpp`

### 2-3. 温度モデル
- 温度は「鉄の状態」として毎フレーム自然冷却（プレイヤーが歩いていても冷える）
- 炉で加熱・打撃で金床に熱が逃げる。一定温度以上で表面から火花（＝加熱完了の合図）
- 温度 → 色（暗い赤 → 橙 → 黄 → 白）で表示

### 2-4. 武器のモーフ（頂点補間）
- Blender で作った**同じトポロジー**の FBX（粗い素材 `stage_0` → 完成品 `stage_final`）を読み込み、進捗に応じて**頂点補間**
- 区画ごとに進捗を持ち、叩いた区画だけが変形する
- 照準・描画・進捗が**同じ区画分割の規約**を使うのでズレない

### 2-5. 研ぎ車（足踏み式砥石）
- 1回の踏み込み＝**角速度の力積**、間は摩擦で減速：dω/dt = −kω
- 解析解 ω *= exp(−k·dt) で積分 → **フレームレート非依存**
- 刃を当てると抵抗が増える → 一定のリズムで踏み続ける必要がある
- 📁 `Physics/GrindWheel.h/.cpp`

### 2-6. CPU パーティクル
- 3種類のプール
  - 火花：**重力＋地面でバウンド**
  - 火の粉（余燼）：**浮力**で上昇しながら揺れて消える
  - 焼入れの蒸気：**浮力＋空気抵抗**で減速しながら膨らむ
- 描画はカメラ向きの**ビルボード＋加算合成**
- 📁 `Physics/Particles.h/.cpp`

### 2-7. 歩行の衝突判定（2D）
- 床を歩くだけなので 3D を**上から見た 2D（XZ 平面）**に落とした
- プレイヤー＝**円**（上から見たカプセル）→ 角に引っかからず滑らか
- 衝突形状（コリジョンプロキシ）はモデルから**自動生成**
  - 道具：頂点を床に投影した**凸包**（Andrew's monotone chain）
  - 建物（凹形状）：腰の高さで水平に**断面スライス**した線分 → 戸口は自然に通れる
- 応答＝**押し出し**（接触法線方向に重なり分だけ戻す）→ 残った成分で**壁ずり**
- 蝶番で開くドア（`HingedDoor`）
- 📁 `Physics/Collision2D.h/.cpp`, `SceneForge/Collision.cpp`

### 2-8. フレームレート非依存の補間
- `a = lerp(a, target, 1 − exp(−λ·dt))`（指数減衰による平滑化）
- 30fps でも 144fps でも同じ動き
- 📁 `GameLogic/Lerp.h/.cpp`

## 4. レンダリング（実装済み）

### 4-1. パイプライン全体の流れ
```
[シャドウパス] 太陽から深度だけ描く（2048² の深度テクスチャ）
      ↓
[シーンパス] HDR のオフスクリーン RT（R16G16B16A16_FLOAT）へフォワード描画
   不透明（壁・床・道具・PBR） → 発光（鉄・炭） → 半透明（水・パーティクル）
      ↓
[ポストプロセス] ブルーム（輝度抽出 → 横ブラー → 縦ブラー）
      ↓
   FXAA ＋ ACES トーンマッピング → sRGB のバックバッファへ出力
```

### 4-2. 一覧

| 技術 | 内容 | 選定理由・ポイント |
|---|---|---|
| **フォワードレンダリング** | 全物体をライティング込みで1パス描画 | 光源が少ない（太陽＋炉火）・半透明と発光が多い・内蔵 GPU で G-Buffer の帯域を節約（→ 5章参照） |
| **リニア空間ライティング** | 色テクスチャは `R8G8B8A8_UNORM_SRGB` で読み込み（GPU が自動でリニア化）、法線・ラフネスはリニアのまま。出力 RTV も sRGB | 光の足し算・掛け算はリニア空間でないと物理的に正しくならない |
| **HDR レンダリング** | 16bit 浮動小数点の RT に 1.0 を超える明るさを保持 | 白熱した鉄や炭の「眩しさ」を潰さずに残す |
| **ACES トーンマッピング** | Narkowicz 2015 の近似式で HDR → 0〜1 へ S 字カーブで圧縮 | 白飛びせず映画的な階調。FXAA を切っても必ず通る様にした |
| **ブルーム** | 閾値で明部を抽出 → 分離可能なガウシアンブラー（横・縦） → 加算 | 熱い鉄・炭が「光って見える」 |
| **FXAA** | エッジだけを検出して均すアンチエイリアス（1パス） | MSAA より軽い。テクスチャのちらつきは mipmap で対処 |
| **物理ベースレンダリング（PBR）** | Cook-Torrance BRDF：D=GGX、G=Schlick-GGX、F=Schlick。メタリック / ラフネスのワークフロー。非金属 F0 = 0.04 | 小屋の石壁・床・地面に適用（Poly Haven の実写 PBR テクスチャ） |
| **ノーマルマップ** | 頂点に接線を持たず、ピクセルシェーダー内の**スクリーン空間微分（ddx/ddy）で接線空間を復元**（cotangent frame） | メッシュに接線データが無くても使える |
| **シャドウマップ** | 太陽＝平行光源 → **正射影**で深度を描画。2×2 のバイリニア PCF でエッジを柔らかく。**法線オフセット**でシャドウアクネ対策。太陽が動かない間は**再描画しない（キャッシュ）** | 暗い室内に窓から差す光と影 |
| **炉火の点光源** | 炉の位置から逆二乗減衰の光を PBR / 道具に加算 | 火が部屋を照らす |
| **道具のライティング** | ランバート拡散＋ブリン-フォン鏡面＋影＋炉火 | 軽量 |
| **トリプラナー投影** | UV を使わず XYZ 3方向から石テクスチャを投影し法線で混ぜる。**オブジェクト空間**で投影するので炉を動かしても模様が滑らない | 炉のモデルの UV の継ぎ目で石の大きさが揃わない問題の解決 |
| **熱色（温度 → 色）** | 温度から暗赤〜白熱の色を決め、発光としてブルームに乗せる | 冷えた鋼はテクスチャ（BaseColor）の地色、発光は温度で駆動 |
| **武器の金属シェーダー** | 2色の半球（空色・地面色）で**擬似的な環境反射**＋フレネル＋研いだ部分は滑らかな地金 | IBL の安価な代用 |
| **屈折する水** | シーンをコピーして背後を歪めてサンプル。**深度バッファから水深**を求め浅い所は透明・深い所は濃く。Schlick のフレネル、壁との境に泡の線 | 平面テクスチャに見えない水 |
| **炭シェーダー** | 炭の熱い部分だけを value noise でその場で明滅 | 軽量（内蔵 GPU 向け） |
| **インタラクティブ草** | 真上からの**正射影カメラ**でレンダーテクスチャに「踏まれた跡」を描く（MAX ブレンド）→ 毎フレーム乗算ブレンドで**指数減衰** → 草の頂点シェーダーが**勾配（中心差分）**方向へ倒す | 汎用の `InteractionMap`。将来は炭・床にも流用可 |
| **プロシージャル空＋距離フォグ** | 高さで空色を補間、太陽のハロー。遠景をフォグで馴染ませる | |
| **シェーダーのビルド管線** | `.hlsl → fxc（MSBuild）→ .cso → 実行時 Load`。**D3DReflect** で頂点入力レイアウトを自動生成 | 実行時コンパイルの文字列を廃止 |

> **レンダリングの位置付け**：主役ではなく「物理とシステムを見やすくする支え」。ただしパイプライン全体（リニア空間 → HDR → トーンマッピング）を理解していることを示す。

## 5. 試作済み・未接続（⚠ 発表で「使っている」と言わない）

### 5-1. ディファードレンダリング（Deferred Shading）
- `Deferred.cpp/.h` に **G-Buffer**（アルベド / ワールド法線 / ワールド座標の3枚）と全画面ライティングパスを試作済み・ビルドにも含まれている
- **ただし現在どこからも呼ばれていない＝実際の描画は 100% フォワード**
- **発表での言い方（おすすめ）**：
  「ディファードも試作して比較しました。本作は光源が太陽と炉火の2つだけで、水やパーティクルなど半透明・発光が多く、内蔵 GPU では G-Buffer の帯域コストも大きいので、**フォワードを採用**しました」
  → 「技術選定の理由を語れる」アピールになる（ただし本当に比較したかは自分の言葉で確認してから）

### 5-2. その他
- 武器モーフ・発光鉄条のシェーダーはまだ**実行時コンパイル（文字列）**。他のシェーダーと同じ `.cso` 管線へ移す予定
- SSAA（スーパーサンプリング）の仕組みはあるが倍率 1 ＝無効
