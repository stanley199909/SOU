0. 作品概要（30秒）

  • ジャンル：中世の鍛冶屋で剣を一本鍛え上げる一人称の鍛造シミュレーション
  • 出発点：『Kingdom Come: Deliverance II』の鍛冶ミニゲームの再現 → 現実の鍛造工程（加熱・鍛打・裏返し・研ぎ・焼入れ）へ拡張
  • 環境：C++ / DirectX 11 / HLSL（学校の教材フレームワークがベース。商用エンジン不使用）
  • アピールの軸
    1. 自作の物理シミュレーション（ハンマー・金属の流れ・パーティクル・衝突）
    2. ゲームプレイのシステム設計（階層型ステートマシン＋データ駆動レシピ）
    3. それを見やすくするレンダリングパイプライン一式（リニア空間・HDR・PBR・シャドウ）

1. 設計・アーキテクチャ 実装済み

1-1. 階層型ステートマシン（HSM）

  • 上位：シーンの状態（タイトル / プレイ / リザルト）
  • 下位：プレイ中の工程ステートマシン（1工程＝1状態）
    HeatStep 加熱 / ForgeStep 鍛打 / GrindStep 研ぎ / QuenchStep 焼入れ
  • フレームワーク StateMachine は前作『statemachinechase』から再利用。文字列キーで状態を登録し、std::function で Enter / Update / Exit を持つ
  • 状態機は「いつ遷移するか」を知らない。遷移の判断は持ち主（SceneForge）側

選定理由：工程がはっきり分かれているゲームなので FSM が一番素直。前作で使い慣れていて保守しやすい。

📁 StateMachine/ ・ StateMachine/Player/*Step.cpp

1-2. データ駆動（レシピ）

  • 武器＝「工程の順番＋各工程の案内文」を持つデータ（WeaponRecipe 構造体）
  • 新しい武器を追加する＝レシピを1つ足すだけ。状態機のコードは変えない
  • 同じ工程を何度でも使える（例：鍛打の前と焼入れの前に「加熱」を2回）

不採用：コマンドパターン（undo / replay が要らないので過剰）。

📁 GameData/WeaponRecipe.h/.cpp

1-3. シミュレーションと描画の分離（デカップリング）

  • Physics/ 物理 ・ GameLogic/ 汎用システム ・ StateMachine/ 制御 ・ GameData/ データ ・ SceneForge/ 描画と指揮
  • 例：ForgingSim は「打撃を受けたら鉄がどう変形するか」だけを答える。得点・音・セリフはシーン側が結果（StrikeOutcome）を見て決める
  • 効果：見た目を作り直しても（アニメ外注など）ゲームの正しさが崩れない

1-4. ステージエディタ（データ駆動の配置）

  • 専用シーンでクリック選択・XYZ ギズモで道具を配置 → stage_layout.txt に保存 → ゲーム本編が同じファイルを読む
  • マウスからのレイキャストによるピッキング（逆投影）、炉を動かすと炭・火の粉が付いてくる親子関係

📁 StageEditor.cpp

1-5. AABB アンカーによる自動配置

モデル読込時に AABB（軸平行境界ボックス）を計算し、「金床の上面中心」等のアンカーへ自動で乗せる。モデルを差し替えても座標の手調整が不要。

1-6. アセット共有とシーン切替の高速化

モデルはルートシーンが所有し、サブシーンは参照だけ。テクスチャはパスをキーにしたキャッシュ（TextureCache）で一度だけデコード。→ シーン切替時の 4〜5 秒の停止を解消。

1-7. チューニング値の外部化（マジックナンバー排除）

数値は名前付き定数・ImGui のスライダ・テキストファイル（forge_tuning.txt 等）に集約。F1 でデバッグ UI、見えないシステム（当たり判定など）はデバッグ描画で可視化。

2. 自作の物理シミュレーション ★ 実装済み

2-1. ハンマー：ばね-ダンパモデル

  • 質量 m のハンマー頭が自然長のばねに付いているモデル
  • 合力＝復元力（フックの法則 −kx）＋減衰力（−cv） → 加速度 → セミインプリシット・オイラー法で積分
  • 打撃時に力積 J を与えて初速 v0 = J/m → オーバーシュートしてから静止位置に収束
  • 剛性 k・減衰 c・質量 m はスライダで調整可（臨界減衰 = 2√(km)）

選定理由：計算が軽く、陽的オイラー法より安定（エネルギーが発散しにくい）。

📁 Physics/HammerPhysics.h/.cpp

2-2. 鉄の変形：体積保存のハイトフィールド

  • 鉄を 20×6 のグリッド（高さ場）で持つ（長さ5区画 × 表裏2面で進捗管理）
  • 叩いたセルの高さを目標に近づけ、押し出した分を余剰の少ない近傍セルへ重み付きで再分配
  • 重みを正規化（合計1）するので総体積が保存される（金属は非圧縮）。叩くほど目標形状に収束
  • 結果を Shaped / ColdHit / OverHit / AlreadyDone で返す

📁 Physics/ForgingSim.h/.cpp

2-3. 温度モデル

温度は「鉄の状態」として毎フレーム自然冷却（歩いている間も冷える）。炉で加熱・打撃で金床へ熱が逃げる。一定温度以上で表面から火花（＝加熱完了の合図）。温度 → 色（暗赤 → 橙 → 黄 → 白）。

2-4. 武器のモーフ（頂点補間）

  • 同じトポロジーの FBX（粗い素材 stage_0 → 完成品 stage_final）を読み、進捗に応じて頂点補間
  • 区画ごとに進捗を持ち、叩いた区画だけが変形。照準・描画・進捗が同じ区画分割の規約を使うのでズレない

2-5. 研ぎ車（足踏み式砥石）

  • 1回の踏み込み＝角速度の力積、その間は摩擦で減速：dω/dt = −kω
  • 解析解 ω *= exp(−k·dt) で積分 → フレームレート非依存。刃を当てると抵抗が増える

📁 Physics/GrindWheel.h/.cpp

2-6. CPU パーティクル

  • 火花：重力＋地面でバウンド
  • 火の粉（余燼）：浮力で上昇・揺れて消える
  • 焼入れの蒸気：浮力＋空気抵抗で減速しながら膨らむ
  • 描画はカメラ向きビルボード＋加算合成

📁 Physics/Particles.h/.cpp

2-7. 歩行の衝突判定（2D）

  • 床を歩くだけなので 3D を上から見た 2D（XZ 平面）に落とした
  • プレイヤー＝円（上から見たカプセル）→ 角に引っかからない
  • 衝突形状はモデルから自動生成：道具＝床に投影した凸包（Andrew's monotone chain）、建物（凹形状）＝腰の高さの断面スライス線分（戸口は自然に通れる）
  • 応答＝押し出し → 残った成分で壁ずり。蝶番で開くドア（HingedDoor）

📁 Physics/Collision2D.h/.cpp ・ SceneForge/Collision.cpp

2-8. フレームレート非依存の補間

a = lerp(a, target, 1 − exp(−λ·dt))（指数減衰による平滑化）。30fps でも 144fps でも同じ動き。📁 GameLogic/Lerp

4. レンダリング 実装済み

4-1. フレームの流れ

[シャドウパス]   太陽から深度だけ描く（2048² 深度テクスチャ）
      ↓
[シーンパス]     HDR オフスクリーン RT（R16G16B16A16_FLOAT）へフォワード描画
                 不透明（壁・床・道具） → 発光（鉄・炭） → 半透明（水・パーティクル）
      ↓
[ポストプロセス] ブルーム（輝度抽出 → 横ブラー → 縦ブラー）
      ↓
                 FXAA ＋ ACES トーンマッピング → sRGB バックバッファへ

4-2. 一覧

技術内容理由・ポイント
フォワードレンダリング全物体をライティング込みで描画光源が少ない（太陽＋炉火）、半透明・発光が多い、内蔵 GPU で G-Buffer の帯域を節約（→ 5章）
リニア空間ライティング色テクスチャは R8G8B8A8_UNORM_SRGB で読み GPU が自動でリニア化。法線・ラフネスはリニアのまま。出力 RTV も sRGB光の足し算・掛け算はリニア空間でないと物理的に正しくならない
HDR16bit 浮動小数点 RT に 1.0 を超える明るさを保持白熱した鉄・炭の眩しさを潰さない
ACES トーンマッピングNarkowicz 2015 の近似式で HDR → 0〜1 へ S 字カーブで圧縮白飛びせず映画的な階調。FXAA を切っても必ず通る
ブルーム閾値で明部抽出 → 分離可能ガウシアンブラー（横・縦）→ 加算熱い鉄・炭が光って見える
FXAAエッジだけ検出して均す（1パス）MSAA より軽い。テクスチャのちらつきは mipmap で対処
PBRCook-Torrance BRDF：D=GGX、G=Schlick-GGX、F=Schlick。メタリック / ラフネス。非金属 F0=0.04小屋の石壁・床・地面（Poly Haven の実写 PBR テクスチャ）
ノーマルマップ頂点に接線を持たず、ddx/ddy（スクリーン空間微分）で接線空間を復元（cotangent frame）メッシュに接線データが無くても使える
シャドウマップ太陽＝平行光源 → 正射影で深度描画。2×2 バイリニア PCF、法線オフセットでアクネ対策、太陽が動かない間は再描画しない（キャッシュ）暗い室内に窓から差す光と影
炉火の点光源炉の位置から逆二乗減衰の光を加算火が部屋を照らす
道具のライティングランバート拡散＋ブリン-フォン鏡面＋影＋炉火軽量（PBR ではない）
トリプラナー投影UV なしで XYZ 3方向から投影し法線で混ぜる。オブジェクト空間なので炉を動かしても模様が滑らない炉の UV の継ぎ目で石の大きさが揃わない問題の解決
熱色（温度 → 色）温度から暗赤〜白熱の色を決め、発光としてブルームへ冷えた鋼は BaseColor、発光は温度で駆動
武器の金属シェーダー2色の半球（空・地面）で擬似環境反射＋フレネル＋研いだ部分は滑らかな地金IBL の安価な代用（IBL ではない）
屈折する水シーンをコピーして背後を歪めてサンプル。深度バッファから水深（浅い所は透明）、Schlick フレネル、壁との境に泡の線平面テクスチャに見えない水
炭シェーダー熱い部分だけ value noise でその場で明滅内蔵 GPU 向けに軽量
インタラクティブ草真上からの正射影カメラでレンダーテクスチャに踏み跡（MAX ブレンド）→ 乗算ブレンドで指数減衰 → 頂点シェーダーが勾配（中心差分）方向へ倒す汎用 InteractionMap。炭や床にも流用可
プロシージャル空・フォグ高さで空色を補間＋太陽のハロー、遠景は距離フォグ
シェーダービルド管線.hlsl → fxc（MSBuild）→ .cso → Load。D3DReflect で頂点入力レイアウトを自動生成実行時コンパイルの文字列を廃止

位置付け：レンダリングは主役ではなく「物理とシステムを見やすくする支え」。ただしパイプライン全体（リニア空間 → HDR → トーンマッピング）を理解していることを示す。

5. 試作のみ・未接続 発表で「使っている」と言わない

5-1. ディファードレンダリング（Deferred Shading）

  • Deferred.cpp/.h に G-Buffer（アルベド / ワールド法線 / ワールド座標の3枚）と全画面ライティングパスを試作。ビルドにも含まれている
  • ただしどこからも呼ばれていない。実際の描画は 100% フォワード

おすすめの言い方：「ディファードも試作して比較しました。本作は光源が太陽と炉火の2つだけで、水やパーティクルなど半透明・発光が多く、内蔵 GPU では G-Buffer の帯域コストも大きいので、フォワードを採用しました。」

→ 技術選定の理由を語れるアピールになる。本当に比較したかは自分で確認してから使う。

5-2. その他

  • 武器モーフ・発光鉄条のシェーダーはまだ実行時コンパイル（文字列）。他と同じ .cso 管線へ移す予定
  • SSAA（スーパーサンプリング）の仕組みはあるが倍率 1＝無効
